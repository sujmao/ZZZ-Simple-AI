## 📖 第一小節：為什麼AI複雜任務總是"改着改着就亂了"

### ❓ 提問

- 為什麼讓AI改一段代碼，它經常改着改着就偏離目標了？
- 同樣的需求，為什麼AI有時做得很好，有時卻"放飛自我"？

### 📝 術語

- **Plan模式（Plan Mode）**：先制定詳細計劃，經確認後再執行的工作模式
- **執行模式（Act Mode）**：邊想邊幹、直接動手改代碼的模式

### 💬 一句話解釋

AI編程需要"先規劃再動手"，因為模型本身不會自動"三思而後行"——它只會根據當前看到的內容，預測下一個最可能出現的詞。

### 🧐 你可以先這樣理解

想象你請了一個裝修工人（AI）來改造你的房子：

**執行模式（Act Mode）** 就像工人拿到鑰匙就進場，邊看邊改：
- 看到廚房不順眼，拆了重裝
- 拆完發現水管位置不對，又改水管
- 改完水管發現影響客廳佈局，又把客廳拆了
- 三天後你發現房子一團糟，原始格局也找不回來了

**Plan模式** 就像工人先花一天時間：
- 仔細測量每個房間
- 畫出設計圖紙
- 列出材料清單和施工順序
- 給你看過方案、確認無誤後再動手

AI模型本質是按概率"接話"的。任務越短，它越不容易跑偏；任務越長，它越容易"走一步看一步"，逐漸被新信息帶偏，忘記最初的目標。

這就是為什麼長任務容易"改着改着就亂了"——**上下文被新信息淹沒了**。

### 📚 示例

**場景一：用Plan模式寫項目方案（非技術場景）**

❌ **執行模式**：
你直接打開PPT開始寫，寫到第3頁發現邏輯不通，返回修改第1頁；
改着改着發現需要補充數據，又回去找資料；
最後整個方案結構混亂，花了半天時間。

✅ **Plan模式**：
1. **研究階段**：先蒐集所有相關資料，理解項目背景
2. **規劃階段**：列出方案框架——背景→目標→策略→執行→預算
3. **確認階段**：把框架給領導看，確認方向無誤
4. **執行階段**：按框架一步步填充內容，每完成一部分就核對

---

**場景二：讓AI給現有項目添加用户登錄功能（編程場景）**

**執行模式下的AI**：
1. 先看到需要登錄頁面，就創建一個 login.html
2. 然後發現需要後端接口，就創建一個 login.php
3. 寫着寫着發現需要數據庫，就去改數據庫配置
4. 改數據庫時發現權限系統不完善，又去改權限系統
5. 最後登錄功能還沒做好，其他部分卻被改得亂七八糟

**Plan模式下的AI**：
1. **研究階段**：通讀整個代碼庫，理解現有架構
2. **規劃階段**：生成實施計劃——需要改哪些文件、按什麼順序、每步做什麼
3. **確認階段**：把計劃給你看，你確認無誤
4. **執行階段**：嚴格按照計劃一步步實施

### ✅ 你只需要記住

1. AI模型是按概率"接話"的，**任務越長越容易跑偏**
2. Plan模式的核心是**"先規劃再動手"**，不是讓AI變聰明，而是強制它"三思而後行"
3. 這屬於**主線二（駕馭工程派）**——通過設計"作業環境"讓模型可靠工作

---

💭 **上一節我們知道了**：AI編程容易"改着改着就亂了"，是因為模型本質是按概率接話，長任務容易偏離目標。那具體怎麼解決？接下來看Plan模式。

## 📖 第二小節：Plan模式——讓AI"先想後做"

### ❓ 提問

- Plan模式具體是怎麼工作的？
- 主流AI編程工具都支持嗎？

### 📝 術語

- **Plan模式（Plan Mode）**：創建只讀研究階段，在做任何代碼更改之前先分析和規劃
- **只讀研究階段**：AI只能查看代碼，不能修改，用於充分理解代碼庫

### 💬 一句話解釋

Plan模式給AI配了一個"項目經理"角色，強制它先進入"只讀研究"狀態理解代碼庫，生成實施計劃，經你批准後再動手。

### 🧐 你可以先這樣理解

回到裝修工人的比喻：

**執行模式** = 工人拿到鑰匙就進場拆牆
**Plan模式** = 工人先花一天"量房"——只看不動手

Plan模式的設計有三條"剋制"：

1. **不改代碼，直到你點"開始實施"**
   - AI在這個階段只能"看"和"想"，不能"動手"
   - 你掌握最終決策權

2. **只讀探索，充分理解上下文**
   - AI會通讀相關文件，理解項目結構
   - 這就像給模型**擴展上下文**——讓它看到更多相關信息

3. **生成可審計的計劃文檔**
   - 不是黑盒操作，而是產出清晰的計劃清單
   - 你可以審查、修改、確認每一步

**為什麼這能解決問題？**

- **回扣本質一（概率模型）**：把"規劃"和"執行"分離，降低執行階段的隨機性
- **回扣本質二（上下文）**：規劃階段在**擴展上下文**（充分理解代碼庫），執行階段在**約束上下文**（按計劃走，不被新信息帶偏）

### 📚 示例

**主流AI編程工具的Plan模式對比**：

| 產品 | 模式名稱 | 核心特點 |
|:---|:---|:---|
| **CodeBuddy** | Plan Mode | 支持複雜任務規劃，生成詳細實施計劃，與IDE深度集成 |
| **GitHub Copilot** | Plan模式 | 集成在IDE裏，適合日常開發任務 |
| **Cursor** | Agent/Ask模式 | 通過對話方式自然切換規劃和執行 |

---

**使用 CodeBuddy Plan Mode的典型流程**：

```
你：我想給這個項目添加用户權限系統

CodeBuddy：我來啓動Plan模式分析這個項目...
[只讀研究階段：通讀代碼庫，理解現有架構]

CodeBuddy：我分析了項目結構，這是我的實施計劃：
1. 創建用户表遷移文件
2. 添加認證中間件
3. 修改路由配置
4. 創建登錄/註冊頁面
5. 添加權限檢查邏輯

你：第3步我有點擔心，會不會影響現有API？

CodeBuddy：好問題。讓我重新檢查一下API路由...
[調整計劃]

你：確認執行

CodeBuddy：[開始按步驟實施]
```

### 📚 非技術場景：組織部門團建

**Plan模式同樣適用**：

1. **研究**：瞭解預算、人數、時間、大家偏好
2. **規劃**：生成方案——上午拓展→午餐→下午自由活動→晚餐
3. **確認**：把方案發羣裏，收集反饋並調整
4. **執行**：按確認後的方案預訂場地、安排交通

**為什麼這能避免"改着改着就亂了"？**
- 如果不先規劃，可能訂了餐廳才發現有人不吃辣
- 如果不先確認，可能按自己想法安排，結果大家不滿意

### ✅ 你只需要記住

1. Plan模式的核心是**"規劃與執行分離"**——不是讓AI變聰明，而是給它配一個"項目經理"
2. 規劃階段**擴展上下文**（理解全貌），執行階段**約束上下文**（按計劃走）
3. 適合**複雜、多步驟、影響範圍廣**的任務——不管是編程還是寫方案

---

💭 **上一節我們知道了**：Plan模式通過"先規劃再動手"解決了單次任務的失控問題。但項目級的質量和可維護性如何保證？這就需要"先寫需求再動手"了。

## 📖 第三小節：從"寫代碼"到"寫規格"——SDD規範驅動

### ❓ 提問

- Plan模式解決了單次任務的規劃問題，但項目級的代碼質量如何保證？
- 如果AI生成了代碼，半年後出了問題，誰來負責？

### 📝 術語

- **先寫需求再動手**：複雜任務開始前，先寫清楚需求文檔，再讓AI執行
- **需求文檔優先**：把需求説明當作最重要的產出，AI生成的內容要符合需求

### 💬 一句話解釋

> 💡 **先寫需求再動手的核心是"需求文檔優先"——人寫清楚需求，AI按需求生成內容，每步都能追溯到需求條款，讓不確定性被關在籠子裏。**

### 🧐 你可以先這樣理解

想象你是一家餐廳的老闆：

**傳統開發** = 你直接教廚師（AI）做菜
- 你説："做一份紅燒肉"
- 廚師憑經驗做，可能每次味道都不一樣
- 半年後你問："為什麼今天這麼鹹？"——沒人記得當時的配方

**先寫需求再動手** = 你先寫菜譜，廚師按菜譜做
- 你寫："紅燒肉做法——五花肉500g、生抽2勺、老抽1勺、冰糖30g..."
- 廚師按菜譜做，出品穩定
- 半年後味道變了，你查菜譜就知道哪裏出了問題

**三大核心原則**：

1. **一份需求，一個標準**
   - 需求文檔是項目唯一合法的定義
   - AI生成的內容必須與需求嚴格對齊

2. **按規矩來**
   - AI在需求設定的邊界內創作，而非自由發揮
   - 這就是**回扣本質一**——用明確需求約束概率生成

3. **有據可查**
   - 每步AI生成的內容都能追溯到需求中的具體條款
   - 需求文檔是最結構化的**上下文組織形式**（**回扣本質二**）

---

**為什麼這很重要？**

AI生成代碼很快，但"生成"不等於"正確"，更不等於"可維護"。

當項目越來越大，你需要知道：
- 這段代碼為什麼這樣寫？
- 需求變了，該改哪些地方？
- 新成員如何快速理解項目？

> 💡 **需求文檔回答了這些問題。人寫需求，AI生成內容，輸出只是需求的副產品。**

### 📚 示例

**對比"直接生成"和"規格驅動"**：

**方式一：直接讓AI寫功能**
```
你：給我寫一個用户登錄功能
AI：[生成代碼]
半年後：這段代碼誰寫的？為什麼這樣設計？不知道。
```

**方式二：先寫需求再動手**
```
1. 人寫需求文檔：
   - 功能：用户登錄
   - 輸入：用户名、密碼
   - 驗證規則：用户名長度3-20字符...
   - 錯誤處理：用户名不存在→提示"用户名或密碼錯誤"...

2. AI根據需求生成內容

3. 驗證：輸出是否符合需求？

4. 半年後：查需求文檔就知道當初的設計邏輯
```

**代表項目**：

| 項目 | 核心思想 | 特點 |
|:---|:---|:---|
| **OpenSpec** | 規格文件驅動AI生成代碼 | 用形式化規格約束AI輸出 |
| **Superpowers** | 可複用的Skills | Skills本質上就是**規範模板**——把常見任務的規格封裝起來 |

### ✅ 你只需要記住

1. **先寫需求再動手**的核心是"需求文檔優先"——人寫需求，AI生成內容
2. 需求是**唯一標準**，每步輸出都能追溯到需求條款
3. 這是**駕馭工程派**的終極形態——用明確需求把概率模型的不確定性關進籠子裏
