## 📖 第一小節：ChatGPT 時刻——從"能聊"開始

### ❓ 提問

- 為什麼 ChatGPT 成了 AI 時代的"開門時刻"？
- 為什麼它一開始只能"聊"，不能直接幫我訂機票？

---

### 📝 術語

| 項目 | 內容 |
| :--- | :--- |
| **中文** | 網頁聊天機器人 |
| **英文** | Web Chatbot |
| **補充** | ChatGPT 讓這種形式真正進入大眾視野 |

---

### 💬 一句話解釋

> 💡 **説白了，ChatGPT 開啓了"對話即界面"的時代——你打字，它回話，但也就僅限於此了。**

---

### 🧐 你可以先這樣理解

2022 年底，ChatGPT 突然火了。這不是一個簡單的"新產品上線"，而是一個**時代的開端** 🚀。

無數人第一次在網頁裏輸入問題，然後看着 AI 一句一句地回覆。那種感覺就像突然有了一個"什麼都能聊"的夥伴 💬。學生用它寫論文，程序員用它 debug，職場人讓它幫忙寫郵件……它似乎什麼都能聊，但又好像什麼都做不了——你不能真的讓它去查你的日程、訂機票、或者操作公司的系統。

這一階段最重要的變化，其實是**普通人第一次可以直接和大模型對話**。但它的底層並沒有變：它仍然是根據當前對話裏的上下文，按概率生成文字。它能依賴的信息，主要還是訓練時學到的參數知識，以及你眼前這段對話。

換句話説，它看起來是在"聊天"，但實際上還是在做第一章講的那件事：**根據前文，猜下一個詞**。

**❓ 那為什麼不讓它直接做事呢？** 

因為那時候它連"當前對話"以外的信息都看不到，更別説去操作外部系統了。

---

### 📚 示例

**✅ 如果你問：**

```
請用白話解釋一下什麼是週報
```

它通常能回答得不錯。

**❌ 但如果你問：**

```
請告訴我我們公司現在最新的報銷制度
```

它就未必知道，因為這類信息不在它訓練時的參數裏，也沒有被放進當前的上下文。

---

### ✅ 你只需要記住

| 要點 | 説明 |
| :--- | :--- |
| 🏁 **起點** | 最早的大模型產品，最典型的形式是網頁聊天機器人。 |
| 🧠 **本質** | 它看起來像在聊天，但底層還是生成文字的概率模型。 |
| ⚠️ **限制** | 這一階段最大的限制，本質上是可用的上下文不夠——只能看到當前對話。 |

---

💭 **上一節我們回顧了 ChatGPT 時刻**：那時候的 AI 只能看到當前對話，所以答不上公司的新制度。那怎麼辦？答案很簡單——幫它查資料。

## 📖 第二小節：知識增強階段——先查資料再回答

### ❓ 提問

- 大模型明明"學富五車"，為什麼卻答不上公司的新制度？
- 既然參數知識不夠，那怎麼讓模型"看到"它沒學過的東西？

---

### 📝 術語

| 項目 | 內容 |
| :--- | :--- |
| **中文** | 檢索增強生成 |
| **英文** | Retrieval-Augmented Generation |
| **簡稱** | RAG |
| **補充** | 先查資料，再讓模型回答 |

---

### 💬 一句話解釋

> 💡 **説白了，RAG 就是先幫模型"查資料"，把查到的內容塞進上下文，再讓它基於這些新信息回答。**

---

### 🧐 你可以先這樣理解

上一節我們説了，模型只能看到當前對話，所以答不上公司的新制度。怎麼辦？

答案很簡單：**幫它查資料，然後把資料放進上下文** 📚。

參數裏的知識有限，而且會過時。真實場景裏，很多關鍵信息在網頁、知識庫、公司文檔和課程資料裏。RAG 做的事情，就是在用户提問後，系統先去檢索相關資料，再把資料放進上下文，讓模型基於這些資料繼續生成答案。

> 📈 **上下文範圍從這裏開始擴大了**——從"只能看到對話"，變成了"還能看到檢索到的資料"。

---

### 🔄 流程圖

```mermaid
flowchart LR
    A["💬 用户問題"] --> B["🔍 檢索系統"]
    B --> C["📚 知識庫 / 文檔"]
    C --> D["📄 取回相關資料"]
    D --> E["📋 放入上下文（Context）"]
    E --> F["🤖 大模型生成答案"]
```

> 💡 **核心邏輯**：RAG不是讓模型變聰明，而是幫它"看到"更多相關資料。

---

### 📚 示例

比如你問：

```
根據我們團隊的請假制度，幫我寫一條請假申請
```

如果模型沒有看到制度文檔，它可能只能泛泛地寫。

但如果系統先從知識庫裏檢索出請假制度，再把這段資料放進上下文，它通常就能寫得更貼近你們團隊的真實要求。

---

### ✅ 你只需要記住

| 要點 | 説明 |
| :--- | :--- |
| 🎯 **本質** | RAG 不是讓模型突然變聰明。 |
| 🔧 **做法** | RAG 做的事情，本質上是給模型補充更相關的上下文。 |
| 📈 **擴展** | 上下文範圍從這裏開始擴大：從只能看到對話，變成了還能看到檢索到的資料。 |

---

💭 **前兩節解決了"知道更多"的問題**：第1節能對話，第2節能查資料。但下一個問題是——很多任務不是"回答一句話"就結束了，而是要真的去做事。AI 怎麼才能真的"動手"？

## 📖 第三小節：工具調用階段——讓 AI 能"動手"

### ❓ 提問

- AI 只會"説"還不夠，怎麼讓它真的"做"？
- 為什麼 AI 不能直接動手，非要通過"表達意圖"這種拐彎的方式？

---

### 📝 術語

| 項目 | 內容 |
| :--- | :--- |
| **中文** | 工具調用 / 函數調用 |
| **英文** | Tool Calling / Function Calling |
| **補充** | 模型表達意圖，外層系統負責執行 |

---

### 💬 一句話解釋

> 💡 **説白了，工具調用就是讓模型學會"發號施令"——它告訴你該調用什麼工具、傳什麼參數，但真正動手的是外層系統。**

---

### 🧐 你可以先這樣理解

很多任務不是"回答一句話"就結束了，而是要真的去做事。

但到了這一步，我們終於明白一件事：**大模型本質上是生成文字的概率模型，它不能直接操作外部世界。** 它既不能真的點開日曆，也不能真的發送郵件。那怎麼辦？

辦法是：**讓模型"表達意圖"** 🎯。

系統先把工具的説明（功能、參數、返回值）放進上下文，模型讀完後，輸出"我要調用哪個工具、參數是什麼"的意圖；外層應用執行後，再把結果放回上下文，模型基於新結果繼續生成。

> 📈 **上下文範圍再次擴大**——從"能看到對話+資料"，變成了"還能看到工具説明和執行結果"。

---

### 🔄 流程圖

```mermaid
flowchart LR
    A["🎯 用户目標"] --> B["📋 工具説明進入上下文（Context）"]
    B --> C["🤖 大模型輸出調用意圖"]
    C --> D["⚙️ 外層應用執行工具"]
    D --> E["📋 執行結果回到上下文（Context）"]
    E --> F["🤖 大模型繼續生成下一步內容"]
```

> 💡 **核心邏輯**：模型只是"發號施令"，真正動手的是外圍系統。

---

### 📚 示例

比如你説：

```
幫我把今天下午三點的組會記進日曆，並提醒我提前十分鐘準備
```

模型不會真的自己去點開日曆。

它會先根據工具説明，輸出調用日曆工具的意圖。然後外層應用去真正創建日程，再把結果返回給模型。

---

### ✅ 你只需要記住

| 要點 | 説明 |
| :--- | :--- |
| 👔 **角色** | 工具調用時，大模型更像決策層，不是執行層。 |
| 🗣️ **方式** | 它不是在親手調用工具，而是在表達調用意圖。 |
| 📈 **擴展** | 上下文範圍再次擴大：從能看到對話+資料，變成了還能看到工具説明和執行結果。 |

---

### 🌉 補充：MCP——讓工具連接更標準化

> 💡 **一句話理解**：MCP 就是給"工具如何連接"定個標準，讓模型和外部工具的連接更規範、更可複用。

當工具越來越多、接入方式五花八門時，一個問題浮現了：**每個工具都要單獨對接嗎？**

MCP（模型上下文協議，Model Context Protocol）就是解決這個問題的一個標準化嘗試。它定義了一套通用的連接規範，讓外部工具和數據源可以按照統一的方式接入，模型也能用統一的方式來發現和調用它們。

**MCP 的核心價值**：
- 🔌 **標準化接口**：不用為每個工具寫不同的接入代碼
- 📦 **可複用連接**：同一個 MCP 服務，可以被不同的 AI 應用共用
- 🏗️ **生態建設**：工具提供者按標準開發，AI 應用按標準接入

> 💡 **補充：MCP 是什麼？**
> 
> 前面説每個工具都要單獨對接，當工具越來越多時，就需要一個統一標準。MCP（模型上下文協議）就是 2024 年底出現的這樣一個標準，讓工具連接更規範。它不是"工具調用"階段就有的，而是後來為了讓連接更規模化而出現的標準化設計。這裏先知道有這個東西，後面會詳細講。

---

💭 **第3節解決了"能動手"的問題**，但新問題又來了：模型雖然能決定調用什麼工具，但它不夠穩——有時候該調 A 卻調了 B，有時候多調或少調了步驟。怎麼辦？

一個務實的選擇是：**在模型外部先把步驟寫死**。外層系統會提前規定先做什麼、後做什麼、哪一步用什麼工具、結果怎麼往下傳。這樣做的好處是穩定、可控，等模型更強了再逐步放權。

這就是工作流出現的背景——它是階段性的妥協，但也是務實的選擇。

## 📖 第四小節：工作流階段——讓模型在"軌道"上跑

### ❓ 提問

- 工具接進來了，為什麼還需要"流程"來管？
- 既然模型能自己決定調用工具，為什麼還要人工寫死流程？

---

### 📝 術語

| 項目 | 內容 |
| :--- | :--- |
| **中文** | 工作流 |
| **英文** | Workflow |
| **補充** | 把多個固定步驟預先串起來的一套外部流程 |

---

### 💬 一句話解釋

> 💡 **説白了，工作流就是"先讓模型在軌道上跑"——因為那時候模型還不夠穩，容易跑偏，所以人先把步驟寫死。**

---

### 🧐 你可以先這樣理解

工具調用出現後，新問題又來了：模型雖然能決定調用什麼工具，但它不夠穩。有時候該調 A 卻調了 B，有時候多調或少調了步驟。

所以這個階段的做法是：**在模型外部先把步驟寫死** 📋。

外層系統會提前規定先做什麼、後做什麼、哪一步用什麼工具、結果怎麼往下傳。

這樣做的好處是穩定、可控。但代價也很明顯：靈活性不足，遇到流程外的情況容易卡住。

> 📈 **上下文範圍繼續擴大**——從單步的工具調用，變成了多步驟的中間結果和流程狀態。

---

### 📊 工作流階段特點

| 維度 | 工作流階段的表現 |
| :--- | :--- |
| 🤔 **為什麼會出現** | 模型當時的自主性和穩定性還不夠強 |
| ✅ **優勢** | 穩定、可控、容易複用 |
| ⚠️ **侷限** | 靈活性不足，流程外情況容易卡住 |
| 🎯 **本質回扣** | 上下文範圍擴大：+ 多步驟的中間結果 |

---

### 📚 示例

比如一個常見流程是：

```
先讀取會議紀要 -> 再提取待辦事項 -> 再整理成周報草稿 -> 最後發給負責人確認
```

這個流程在重複任務裏很好用，因為每一步都提前設定好了。

但如果中間突然出現新的目標，或者資料格式和預設不一樣，工作流就可能接不住。

---

### ✅ 你只需要記住

| 要點 | 説明 |
| :--- | :--- |
| 🤔 **原因** | 工作流階段出現，是因為模型當時還不夠強，需要外部流程來約束。 |
| ⚖️ **權衡** | 優勢是穩定、可控、容易複用；侷限是靈活性不夠。 |
| 📈 **擴展** | 上下文範圍繼續擴大：從單步的工具調用，變成了多步驟的中間結果。 |

---

💭 **第4節用固定流程解決了"穩定性"的問題**，但代價是靈活性不足。如果模型變強了，是不是可以給它更多自主權？這就來到了智能體階段。

固定步驟太僵化，遇到流程外的情況容易卡住，無法處理複雜、開放的任務。但完全放手給模型，它又可能跑偏。怎麼辦？

一個務實的思路是**漸進式放權**：不是一下子把所有決策都交給模型，而是讓模型參與局部決策（比如具體怎麼措辭、選哪個工具），同時保留外部系統的大框架（目標檢查、邊界控制、循環管理）。隨着模型變強，再逐步擴大決策範圍。

這就是智能體出現的背景——它不是人與模型的對立，而是協作。

## 📖 第五小節：智能體階段——圍繞目標自主執行

### ❓ 提問

- 固定流程不夠用了，AI 怎麼變得更"靈活"？
- 那模型變強了，是不是就不需要外部流程了？

---

### 📝 術語

| 項目 | 內容 |
| :--- | :--- |
| **中文** | 智能體 |
| **英文** | Agent |
| **補充** | 圍繞一個目標持續完成多步任務的 AI 應用 |

---

### 💬 一句話解釋

> 💡 **説白了，智能體（Agent）就是讓模型在更大的範圍內"自主發揮"——它不再只是按固定步驟走，而是圍繞目標自己決定怎麼做。**

---

### 🧐 你可以先這樣理解

到了智能體階段，AI 不再只是答一句或執行固定流程，而是**圍繞一個目標連續工作** 🎯。

模型能力變強後，原來必須寫死的部分步驟，可以交給模型自己做局部決策。但底層還是同一個概率模型，只是外層系統把目標、工具、結果和更長的上下文組織得更完整了。

> 📈 **上下文範圍擴大到最大**——除了對話、資料、工具、中間結果，還包括目標、規劃、反思等元信息。模型基於這些更豐富的上下文，來決定下一步做什麼。

---

### 🎒 關於"技能（Skill）"

智能體不是憑空就能做所有事的。為了讓它能處理特定類型的任務，系統通常會提供**技能（Skill）**——可以理解成一種"能力包"，把某類任務常用的説明、工具入口和執行規則提前整理好。

技能本身不是新的大腦，也不是替代模型。它的作用是在需要時，把一類任務的説明和約束更穩定地放進上下文，讓模型知道"這類任務通常怎麼做"。

---

### 📊 工作流 vs 智能體對比

| 維度 | 📋 工作流 | 🤖 智能體（Agent） |
| :--- | :--- | :--- |
| **步驟安排** | 主要靠人工預先寫死 | 可以由模型參與動態調整 |
| **適合任務** | 重複、固定、邊界清楚 | 更復雜、更開放、變化更多 |
| **好處** | 穩定、可控 | 更靈活，更能處理非標準任務 |
| **主要風險** | 流程僵化 | 多步任務更容易跑偏，權限和成本更難控制 |
| **本質回扣** | 上下文範圍：多步驟的中間結果 | 上下文範圍：+ 目標、規劃、反思等元信息 |

### 📚 示例

比如你説：

```
幫我準備明天的課程展示：先整理資料，再列一個提綱，最後給我一版三分鐘發言稿
```

如果只是普通聊天機器人，它更可能只給你一段泛泛的回答。

但智能體形態的系統，會更像是在圍繞這個目標連續工作，把不同步驟的結果繼續放回上下文，再推進下一步。

## 📝 本章要義

> 💡 **一句話核心結論**：AI 產品從"能聊"到"能做"的演進，本質上是**上下文範圍不斷擴大**的過程——模型始終是那個"接話"的概率模型，只是我們能幫它把"接話的依據"給得越來越充分。

### 🔗 核心脈絡回顧：五個階段的必然演進

| 小節 | 階段 | 當時的矛盾 | 解決之道 | 上下文擴展 |
| :--- | :--- | :--- | :--- | :--- |
| 📖 第1節 | 💬 ChatGPT | 普通人想對話，但技術門檻高 | 網頁聊天界面 | 只能看到對話 |
| 📖 第2節 | 🔍 RAG | 模型知識有限且過時 | 先檢索再生成 | + 外部知識庫 |
| 📖 第3節 | 🛠️ 工具調用 | 只會説，不會真的做 | 模型發指令，系統執行 | + 工具説明和執行結果 |
| 📖 第4節 | 📋 工作流 | 模型調用工具不穩定 | 外部流程兜底 | + 多步驟的中間結果 |
| 📖 第5節 | 🤖 智能體 | 固定流程太僵化 | 模型參與動態決策 | + 目標、規劃、反思等元信息 |

**核心規律**：每一階段的出現，都是因為前一階段的**主要矛盾暴露**，而當時選擇了**最務實的解決方案**。

### 🎯 回到兩個本質

**本質一：概率模型——它始終沒變**

| 為什麼體驗差異這麼大？ | 因為**上下文的組織方式**變了 |

**本質二：上下文——演進的真正驅動力**

| 問題 | 深入理解 |
| :--- | :--- |

| 後面技術會怎麼發展？ | 繼續擴大和優化上下文（記憶、多模態、實時信息） |

```

         • 第2階段：+ 檢索資料
         • 第3階段：+ 工具結果
         • 第4階段：+ 流程狀態
         • 第5階段：+ 目標規劃
```

### 🧩 核心洞察：模型能力 vs 系統組織

五個階段演進的背後有一個核心規律——

> **模型本身的能力增長是漸進的，但用户期望它能做的事情越來越多、越來越複雜。**

解決之道不是"等模型變強"，而是**在模型不變的情況下，通過更好的系統設計，把它的能力發揮到極致**。

| 階段 | 當時的妥協 | 為什麼是務實的 |
| :--- | :--- | :--- |
| RAG | 不重新訓練模型，而是外接知識庫 | 成本低、見效快、可定製 |
| 工具調用 | 模型不直接執行，而是發指令 | 安全可控、易於審計 |
| 工作流 | 人先寫死流程，模型在框內發揮 | 穩定可靠、建立信任 |
| 智能體 | 逐步放權，保留兜底 | 靈活與可控的平衡 |

### 📖 自己動手：觀察你用的 AI 產品
